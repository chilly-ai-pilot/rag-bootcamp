## 失败案例深度分析

### ❌ 案例1：ID 3 - SmartBulb-300 断电后记忆功能怎么关闭？

**Ground Truth**：
- 文档：doc3
- 位置：357-389
- 答案："断电后重新上电，灯泡会恢复断电前的亮度和色温状态，无需重新设置。"

**问题诊断**：

**切块边界问题**：
```
块2 (160-360): ...尝试在 APP 中重置 Zigbee 连接。断电后重新上电，灯泡会恢复断电前的亮度和色温状态，无需重新设置。
                                                        ↑ Ground truth 在此结束 (389)
块3 (320-520): 断电后重新上电，灯泡会恢复断电前的亮度和色温状态，无需重新设置。此功能可在 APP 中关闭，改为上电默认白光。
                                                        ↑ 但真正回答"怎么关闭"的内容在这里
```

**根本原因**：
1. 答案被切在块边界（357-389 横跨块2末尾和块3开头）
2. Ground truth 标注只覆盖了"会恢复状态"，但问题问的是"怎么关闭"
3. 真正回答"怎么关闭"的句子（"此功能可在 APP 中关闭"）在 ground truth 范围之外
4. 即使向量检索找到了正确的块，也会因为标注范围问题被判 miss

**解决方向（Iteration 2）**：
- 增大 overlap（如 40 → 80 字），确保完整答案不被切断
- 或使用语义边界切块（按段落切），保持语义完整性
- 修正 ground truth 标注，扩展到包含完整回答

---

### ❌ 案例2：ID 7 - SmartPlug-400 的充电保护功能是怎样工作的？

**Ground Truth**：
- 文档：doc6
- 位置：321-360
- 答案："检测到设备电流在短时间内下降至接近零，判定设备充满电，自动关闭插座，防止过充。"

**LLM 回答**：
```
未找到充分依据。资料中仅提到SmartPlug-400支持过载保护（当负载功率超过2500W持续5秒后自动断电），
未提及充电保护功能的具体工作原理。[文档6:片段1]
```

**问题诊断**：

**语义表达差异**：
- 查询用词：**"充电保护功能"**
- 文档用词：**"防止过充"**（原文中没有"充电保护"这个词组）
- 周围上下文："倒计时关闭"、"循环定时"，跟"充电保护功能"的语义关联度不够强

**检索结果**：
- 向量检索找到了"片段1"（讲过载保护），而不是包含正确答案的"片段2/3"
- 说明向量模型没能将"充电保护功能怎样工作"映射到"检测电流下降防止过充"

**根本原因**：
1. **纯语义鸿沟**：查询和文档使用了不同的术语体系
2. 原文描述比较隐晦，没有明确提到"充电保护"这个概念
3. 向量检索依赖语义相似度，当表达差异过大时会失效

**解决方向**：
- **Iteration 3（Hybrid Search）**：加入 BM25 关键词检索
  - "过充"关键词能直接匹配到正确答案
  - 向量检索 + BM25 融合，互补各自短板
- 或改进文档质量：统一术语，明确概念名称

## 技术验证

### ✅ 已验证的能力

1. **语义理解**
   - 能识别同义词、改写、口语化表达
   - 例："摄像头晚上能看多远" ≈ "红外夜视距离"

2. **中文语义建模**
   - bge-base-zh 在中文场景下表现优异
   - 无需额外微调即可达到 94% 召回率

3. **小规模高质量语料检索**
   - 在 7 篇文档、32 个查询的规模下表现接近完美
   - 证明向量检索适合企业内部知识库等场景

### ⚠️ 已发现的局限

1. **切块边界敏感**
   - 答案被切断时，语义完整性受损，检索效果下降
   - 需要 Iteration 2 优化切块策略

2. **术语不一致时的脆弱性**
   - 当查询和文档用不同术语描述同一事物时，纯向量检索可能失效
   - 需要 Iteration 3 的 hybrid search 补充关键词匹配

3. **依赖文档质量**
   - 文档描述隐晦、术语混乱时，检索效果受影响
   - 这是数据质量问题，不是算法问题

## 生产就绪度评估

### ✅ 可以用于生产的部分

1. **核心检索能力**
   - 94% 召回率在许多实际场景下已足够
   - 语义理解能力强，用户体验好

2. **系统稳定性**
   - ChromaDB 持久化存储，断电不丢数据
   - 延迟加载 + 单例模式，资源使用合理

### ❌ 不能直接用于生产的部分

1. **单一检索策略**
   - 纯向量检索对精确匹配不够鲁棒
   - 需要 hybrid search 补充

2. **缺少 rerank**
   - Top-5 的排序完全依赖向量相似度
   - 可能不够精确，需要 Iteration 4 加 reranker

3. **无拒答机制**
   - 即使检索不到相关内容，也会尝试生成答案
   - 需要 Iteration 6 的拒答阈值

4. **无评估闭环**
   - 手动运行评估，无法持续监控
   - 需要 Iteration 7 的自动化流程

## 后续迭代路径

根据本次实验结果，后续迭代优先级：

### 🔥 高优先级（直接影响未命中的 2 个案例）

1. **Iteration 2（Chunking 优化）**
   - 解决 ID 3（切块边界问题）
   - 实验：增大 overlap 或语义边界切块
   - 预期提升：chunking_sensitive 从 0.80 → 0.90+

2. **Iteration 3（Hybrid Search）**
   - 解决 ID 7（术语不一致问题）
   - 加入 BM25 关键词检索 + RRF 融合
   - 预期提升：exact_match 保持 1.00，overall 从 0.94 → 0.97+

### 📊 中优先级（提升生成质量）

3. **Iteration 4（Reranker）**
   - 虽然 Recall@5 已经很高，但 top-5 内部排序可能不准
   - 加入 bge-reranker 对召回结果重新排序

4. **Iteration 5（LLM-as-Judge）**
   - 自动化评估 faithfulness 和 answer relevance
   - 替代当前的人工抽查

### 🛡️ 低优先级（工程化和安全）

5. **Iteration 6（拒答机制）**
   - 基于 rerank 分数设置拒答阈值

6. **Iteration 7（评估闭环）**
   - CI/CD 集成，每次改动自动跑评估
