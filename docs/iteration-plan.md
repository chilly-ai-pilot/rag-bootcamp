# 模拟真实RAG系统 —— 可迭代工程计划

## 整体设计思路

这个项目按"先建评估,再建系统"的顺序展开,原因很直接:如果没有一套能量化的评估标准,你后面每加一层优化(chunking、hybrid、rerank),都没法判断到底是真的变好了,还是幻觉换了一种方式出现。这也是你之前在阈值调优那轮已经想清楚的逻辑——没有可证伪的东西,就没法调试。

每一次迭代都遵循同一个模板:

1. **这次迭代解决的是哪个具体问题**(对应你最开始拆的四条幻觉根因,或者是新暴露出的工程问题)
2. **为什么选这个技术方案,而不是别的**
3. **怎么验收**——用什么指标证明这次迭代确实变好了
4. **产出物**——这次迭代结束你手上应该有什么

---

## Iteration 0:先立评估基线,再碰系统

**目的**

在写任何检索/生成代码之前,先做两件事:构造一个领域测试集,搭好评估脚本框架。这一步的意义是把"这次改动有没有效果"从主观感觉变成可以跑出数字的东西。

**具体做什么**

- 选一个你熟悉的小领域做语料(比如公司内部的产品文档、或者某个垂直领域的公开资料,50~200篇文档规模足够练手,不需要一开始就上百万文档)
- 人工或半自动构造 30~50 条测试query,每条配上:标准答案、应该被检索到的正确文档片段(ground truth passage)
- 这一步同时用上你之前想到的"构造性数据"思路:除了真实query,再人为造一批"错误claim"(替换实体、替换因果关系、跨片段拼接),作为后面faithfulness检验的测试集

**为什么这么选**

- 测试集規模小(30~50条)是刻意的——这个阶段目标是能跑起来、能看到数字变化,不是覆盖度。规模可以在Iteration 7之后再扩到100~300条(生产级参考规模)
- 不用LangChain/LlamaIndex这类重框架起步,先用纯Python手写。原因:这些框架把检索、chunking、prompt拼接都封装掉了,初期用框架会让你看不到每一步具体发生了什么,等你对每一层都有手感之后,再引入框架做工程化封装更合适

**验收标准**

跑通一次"query → 空的retrieve函数(先返回随机文档) → 生成 → 打分"的完整链路,哪怕分数很差,链路必须先通。

**产出物**:测试集文件(query + 标准答案 + ground truth passage)、评估脚本骨架

## Iteration 1:Naive RAG Baseline

**目的**

先做一个最简单、最原始的RAG——单一向量检索、无rerank、无hybrid——作为后续所有优化的对照组。你要清楚地知道"什么都不做"的效果是多少分,后面每一层优化才有意义。

**技术选型**

| 组件 | 选择 | 为什么 |
|---|---|---|
| Embedding模型 | `bge-base-zh` (BAAI开源中文向量模型) | 你的对话场景是中文,选专门针对中文优化的embedding模型,比直接用OpenAI的通用embedding在中文语义检索上表现更稳定,而且是开源免费的,适合学习项目反复实验 |
| 向量库 | ChromaDB | 本地起步,零运维成本,几行代码起一个持久化向量库。对比pgvector(生产环境常见选择),ChromaDB更适合个人学习项目,不需要先搭Postgres,等你确认整个流程跑得通、想练习生产部署时,再迁移到pgvector |
| 生成器LLM | DeepSeek(API) | 你现在就在用,直接调用API最省事,而且LLM在遵循"只根据给定文档回答"这类指令上表现稳定,适合作为baseline生成器 |
| Chunking | 固定长度切块(比如200字,40字重叠),先不做优化 | 这是baseline,故意留粗糙,好让Iteration 2的优化有对比基准 |

**验收标准**

用Iteration 0的测试集跑一遍,记录:检索命中率(Recall@K,检索到的文档里有没有包含ground truth passage)、生成答案的faithfulness粗略人工打分(先不上LLM-as-judge,人工看10条就行)

**产出物**:能跑通的最简RAG pipeline + baseline分数

---

## Iteration 2:Chunking 优化

**目的**

这一步对应你之前搜索结果里提到的"chunking是被低估的杠杆"——如果baseline的检索命中率很差,大概率问题出在切块粒度,而不是embedding模型或检索算法本身。

**具体做什么**

至少对比三种切块策略:

1. 固定长度切块(baseline,已有)
2. 按语义边界切块(按段落/按标题切,而不是死板按字数切)
3. 更小粒度+滑动窗口重叠(比如100字,50字重叠)

**为什么这么选**

不是直接选"最好的"一种方案,而是先做对比实验——因为chunking的最优策略高度依赖你的文档结构(技术手册和新闻文章的最优切法完全不同),没有实验数据,选型就是拍脑袋。

**验收标准**

同一批测试集,分别跑三种切块策略,对比Recall@K的变化。这一步应该是整个项目里,你能看到分数提升最明显的一次迭代。

**产出物**:三种chunking策略的对比数据 + 确定下来的最优切块方案

---

## Iteration 3:Hybrid Search(向量检索 + BM25关键词检索)

**目的**

解决纯向量检索的一个已知短板:语义相近但关键词精确匹配的场景(比如产品型号、法律条款编号、专有名词),向量检索容易漏掉,BM25关键词检索反而更准。这对应你搜索结果里提到的"2026年hybrid search已经是生产基线"这个行业共识。

**技术选型**

| 组件 | 选择 | 为什么 |
|---|---|---|
| 关键词检索 | `rank_bm25`(Python库) | 轻量,不需要额外起服务,适合学习项目。生产环境通常用Elasticsearch或OpenSearch,但那一套运维成本对学习项目没必要 |
| 融合策略 | RRF(Reciprocal Rank Fusion) | 比简单加权平均更稳健,不需要为向量分数和BM25分数的量纲差异发愁,业界常用做法 |

**验收标准**

对比"纯向量" vs "纯BM25" vs "hybrid"三种方式在同一测试集上的Recall@K,重点看那些包含专有名词/编号的query,hybrid应该在这类query上有明显提升——如果没有,说明你的测试集里这类query样本不够,需要回头补充Iteration 0的测试集。

**产出物**:hybrid检索模块 + 三种检索方式的对比数据

---

## Iteration 4:Reranker

**目的**

对应你最初提到的"rerank机制"——检索召回的top-K文档里,相关性排序未必准确,rerank用一个更精细的模型对召回结果重新打分排序,同时为后续"低于阈值直接拒答"做准备。

**技术选型**

| 组件 | 选择 | 为什么 |
|---|---|---|
| Reranker模型 | `bge-reranker-base`(开源) | 和embedding模型同系列,中文效果有保障,而且是cross-encoder架构(把query和文档一起编码打分),精度比向量检索的bi-encoder架构更高,这正是rerank存在的意义 |

**验收标准**

- 检索到top-20,rerank后取top-5,对比"不rerank直接取top-5" vs "rerank后取top-5"的最终答案faithfulness差异
- 同时记录rerank分数的分布,为后面设计拒答阈值积累数据(这是你之前"先固定阈值,再用测试集跑"那个思路的具体落地)

**产出物**:rerank模块 + rerank分数分布数据(这份数据后面Iteration 6要用)

---

## Iteration 5:LLM-as-Judge 自动化评估

**目的**

这是把你之前设计的"NLI小模型核验"思路,换成业界实际采用的方案——用一个独立的LLM作裁判,自动打faithfulness(答案是否只基于检索到的文档)和answer relevance(答案是否真的回答了问题)两个核心分数,不再靠人工抽查。

**技术选型**

| 组件 | 选择 | 为什么 |
|---|---|---|
| 评估框架 | Ragas | 开源、专门为RAG设计的评估框架,内置faithfulness、answer relevance、context precision等指标,不需要自己从零写评估prompt |
| Judge模型 | 和生成器**不同**的模型/不同的调用 | 关键设计点:如果用同一个模型的同一次生成去评判自己有没有编造,存在你之前已经想到的"自己审自己"逻辑漏洞。做法是用独立的一次API调用,专门用于评判,理想情况下换一个不同的模型(比如生成器用Claude,judge换成另一家模型),成本允许的话务必避免同模型同prompt自证 |

**验收标准**

用Iteration 0构造的"错误claim测试集"(替换实体/因果关系/跨片段拼接三个难度层)喂给judge,看judge能不能正确识别出哪些是编造的——这一步实际上是在评估"评估者本身靠不靠谱",是容易被忽略但很关键的一步。

**产出物**:自动化评估pipeline,每次改动系统后一键跑出faithfulness/relevance分数

---

## Iteration 6:Grounding引用 + 拒答机制

**目的**

把Iteration 4积累的rerank分数分布,和Iteration 5的LLM-as-judge结合起来,做两件事:给答案里每句话标注来源文档、当检索到的文档相关性/faithfulness分数过低时触发拒答或免责声明,而不是硬答。这一步直接对应你最初拆的"硬回答"这条根因,也是RAG流程本身完全没覆盖、需要额外补的那一块。

**具体做什么**

- 拒答阈值:用Iteration 4的rerank分数分布,先设一个初始阈值(比如取分布的某个分位数),低于阈值的检索结果触发"未找到充分依据"提示
- 引用标注:生成答案时要求模型按句标注引用的文档片段编号,再用Iteration 5的judge模型抽查这些标注是否准确(判断"编造内容的同一次生成,标注是否也在编造")

**验收标准**

用Iteration 0里的错误claim测试集,统计拒答机制的准确率——多少比例的编造内容被成功拦截、多少比例的正确答案被误拒(这是precision/recall的权衡,你之前已经想到过这个矛盾)

**产出物**:带拒答机制和引用标注的完整RAG系统

---

## Iteration 7:持续评估闭环

**目的**

把Iteration 5的自动化评估,从"手动跑一次"变成"每次改动自动跑",形成你之前设计的"用真实案例反过来修正阈值"的闭环。这是把整个项目从"能跑的demo"升级到"可维护的系统"的最后一步。

**技术选型**

| 组件 | 选择 | 为什么 |
|---|---|---|
| 自动化触发 | 简单的Python脚本 + 定时任务,或GitHub Actions(如果项目托管在GitHub上) | 不需要上复杂的MLOps平台,学习项目用最轻量的方式把"每次改动跑一遍评估"这个习惯固化下来即可 |
| 测试集扩充 | 把Iteration 0的30~50条,逐步扩到100~300条(参考生产级规模) | 加入你在Iteration 6发现的、被误判的真实案例,让测试集本身随着系统迭代变得更准 |

**验收标准**

任意改动一个组件(比如换一个embedding模型),自动化流程能在几分钟内跑出新的faithfulness/Recall@K分数对比,不需要人工重新走一遍评估流程。

**产出物**:完整的CI式评估闭环 + 迭代到第7轮后的最终系统分数报告

---

## 技术栈总览

```
数据/评估层:  自建测试集(30→300条) + 构造性错误claim数据集
Embedding:    bge-base-zh(开源,中文优化)
向量库:       ChromaDB(学习起步) → pgvector(生产参考)
关键词检索:   rank_bm25 → Elasticsearch/OpenSearch(生产参考)
融合策略:     RRF(Reciprocal Rank Fusion)
Reranker:     bge-reranker-base(cross-encoder)
生成器LLM:    Claude Sonnet API
评估框架:     Ragas
Judge模型:    独立于生成器的模型/调用
自动化:       Python脚本 + GitHub Actions
```

## 迭代顺序背后的逻辑

这七个迭代不是随意排序的,而是刻意让**每一层的问题在下一层被发现**:baseline暴露chunking问题 → chunking优化暴露纯向量检索的短板 → hybrid暴露召回排序不准 → rerank积累的分数分布,恰好是拒答机制需要的原始数据 → judge模型验证完自己靠不靠谱,才有资格去审查生成答案 → 最后把这一切串成自动化闭环。每一步都是在给下一步铺路,而不是七个孤立的优化点。
