# RAG 配置对比：忠实度分析报告

## 概述

本文档对比了两种 RAG 配置在忠实度（Faithfulness）方面的表现，使用 LLM Judge 进行严格的事实核查评估。

**测试数据集**: 32 个查询（chunking_sensitive: 10, exact_match: 11, semantic_paraphrase: 11）

## 配置对比

### 配置 A：保守配置
- **Chunking**: fixed_100_50 (chunk_size=100, overlap=50)
- **Retrieval**: vector (纯向量检索)
- **Rerank**: 无
- **Top-K**: 20

### 配置 B：激进配置
- **Chunking**: fixed_200_40 (chunk_size=200, overlap=40)
- **Retrieval**: hybrid (BM25 + Vector)
- **Rerank**: bge-reranker-base
- **Top-K**: 20

## 整体性能对比

| 指标 | 配置 A | 配置 B | 差异 |
|------|--------|--------|------|
| **平均忠实度** | 0.906 | 0.881 | -0.025 |
| **中位数** | 1.000 | 1.000 | 0.000 |
| **满分案例** | 24/32 (75.0%) | 24/32 (75.0%) | 0 |
| **低分案例** | 8/32 (25.0%) | 8/32 (25.0%) | 0 |

**结论**: 配置 B 的平均忠实度略低，两者满分案例数量相同，但具体案例的表现有显著差异。

- **配置 B 改进**: 找到了 "CR2032×2" 信息但表述不够自信
- **原因**: Hybrid 检索可能找到了 vector 遗漏的相关片段

#### Query 22: 怎样防止摄像头被偷看？

## 根本原因分析

### 配置 A 的特点

**优势：**
1. **清晰的边界**: 100 字符的小 chunk 通常只包含单一产品或单一功能点
2. **精确引用**: 信息来源明确，易于准确标注
3. **稳定性强**: 错误类型较轻，主要是引用标注精度问题

**劣势：**
1. **上下文不足**: 可能遗漏需要完整描述的信息
2. **生成失败风险**: 关键信息被分割到不同 chunk 时可能"未找到依据"

### 配置 B 的特点

**优势：**
1. **完整上下文**: 200 字符的大 chunk 能捕获更完整的信息
2. **召回多样性**: Hybrid 检索结合 BM25 和向量，覆盖更广

**劣势：**
1. **产品边界模糊**: 大 chunk 可能包含多个产品信息，导致归因错误
2. **引用不精确**: 难以准确定位信息在大 chunk 中的具体位置
3. **噪声风险**: Rerank 可能引入相似但不相关的片段
4. **高风险错误**: 容易产生跨产品混淆等严重问题

## 关键发现

### 1. 更复杂 ≠ 更好

配置 B 虽然使用了更复杂的技术栈（hybrid + rerank），但在忠实度上反而略差。这说明在多产品文档场景下，**清晰的边界比完整的上下文更重要**。

### 2. 错误类型的严重性差异

- **配置 A 的错误**: 主要是引用标注不精确、轻微推断，不影响答案的实质正确性
- **配置 B 的错误**: 包括跨产品混淆、完全错误的归因，会导致用户获得错误信息

**4 个改善 vs 4 个恶化**，但恶化案例的严重性远高于改善案例。

### 3. LLM Judge 的价值

LLM Judge 展现了极高的鉴别力：
- 识别出细微的引用标注错误（Query 5: 0.75）
- 发现无依据的推断（Query 27: 0.95）
- 精准识别跨产品混淆（Query 1, 3）
- 严格评估生成失败（Query 8, 31: 0.0）

### 4. Chunk Size 的权衡

| Chunk Size | 优势 | 劣势 | 适用场景 |
|------------|------|------|----------|
| **小 (100)** | 边界清晰，归因准确 | 可能缺失上下文 | 多产品、需要精确归因 |
| **大 (200)** | 上下文完整 | 边界模糊，易混淆 | 单一主题、长文档 |

## 推荐策略

### 优先级排序

基于本次分析，推荐按以下优先级选择配置：

#### 1. 默认推荐：配置 A（保守）

**适用场景：**
- 多产品文档（如本测试场景）
- 对准确性要求极高
- 可以容忍偶尔"未找到依据"

**理由：**
- 更稳定，错误较轻
- 跨产品混淆风险低
- 平均分更高 (0.906 vs 0.881)

#### 2. 条件推荐：配置 B（激进）

**仅当满足以下条件：**
1. 文档是单一产品或主题明确
2. 需要完整的上下文理解
3. 可以接受偶尔的归因错误
4. **必须配合以下改进措施：**
   - 在每个 chunk 中强制包含产品型号标识
   - 优化 rerank 策略，提高精确度
   - 生成时增加产品归属验证逻辑

### 改进建议

#### 针对配置 A 的优化方向

1. **减少生成失败**:
   - 改进 prompt，鼓励模型从多个片段综合信息
   - 考虑适度增加 chunk overlap (50 → 60)

2. **提高引用精度**:
   - 训练模型更准确地标注来源
   - 在生成后验证引用的准确性

#### 针对配置 B 的优化方向

1. **强化产品边界**:
   ```python
   # 示例：在 chunk 元数据中强制包含产品型号
   chunk_metadata = {
       'product': extract_product_name(chunk),
       'section': extract_section(chunk)
   }
   ```

2. **改进 Rerank 策略**:
   - 增加产品型号匹配权重
   - 过滤掉产品不匹配的候选片段

3. **生成验证**:
   ```python
   # 伪代码：验证生成内容的产品归属
   def verify_answer(answer, query, chunks):
       query_product = extract_product(query)
       answer_products = extract_products(answer)
       chunk_products = [c['metadata']['product'] for c in chunks]
       
       # 如果答案提到的产品不在检索片段中，标记为可疑
       if not all(p in chunk_products for p in answer_products):
           return False, "产品归属可疑"
   ```

## 结论

1. **配置 A 更稳定可靠**，平均分更高，错误类型较轻，推荐作为默认配置

2. **配置 B 高风险高收益**，在某些案例中表现更好，但也引入了严重的跨产品混淆问题

3. **Chunk Size 是关键因素**，在多产品场景下，小 chunk (100) 的清晰边界比大 chunk (200) 的完整上下文更重要

4. **LLM Judge 价值巨大**，能够精准识别各种类型的忠实度问题，是评估 RAG 系统质量的有效工具

5. **复杂度不等于质量**，更复杂的检索策略（hybrid + rerank）不一定带来更好的结果，需要根据具体场景选择
