## 🎯 项目整体目标

这是一个 **RAG（检索增强生成）系统的迭代开发训练营**，采用"先建评估，再建系统"的方法论，通过 7 个迭代逐步构建一个生产级的 RAG 系统。

**核心理念**：每次改进都必须用数字证明有效果，避免"感觉变好了"的主观判断。

---

## 📦 Iteration 0（当前阶段）项目结构

这是整个项目的**基线阶段**，目标不是做好，而是**跑通整个链路**。

### **数据层**
```
corpus/
├── doc-1.txt ~ doc-7.txt  # 7篇智能家居产品文档（355~973字）
└── queries.json            # 32条测试查询，每条包含：
                            # - query: 问题
                            # - category: 分类（如 chunking_sensitive）
                            # - doc_id: 答案所在文档
                            # - char_start/char_end: 答案在文档中的精确位置
                            # - ground_truth_text: 标准答案文本
```

### **代码模块**

#### **1. chunking.py（分块模块）**
**职责**：将长文档切成小块，便于检索

**核心函数**：
- `load_corpus(corpus_dir)` → 加载所有文档 `{doc_id: 完整文本}`
- `fixed_length_chunks(text, doc_id)` → 将单个文档切成固定长度的块（200字，重叠40字）
- `build_corpus_chunks(corpus_dir)` → 处理整个语料库，返回所有块的扁平列表

**为什么块大小是200？**  
因为实际文档最小的才355字，如果用500字切块，很多文档就只有一个块，无法测试分块策略的优劣。

---

#### **2. retrieval.py（检索模块）**
**职责**：根据用户查询，从所有块中找出最相关的 k 个

**当前实现**：
- `retrieve_random(query, chunks, k=5)` → **随机返回 k 个块**（完全忽略查询内容）

**为什么用随机？**  
这是 Iteration 0 的刻意设计——建立一个"什么都不做"的性能下限。后续迭代会替换成真正的向量检索。

**未来扩展**：
- `retrieve_vector(...)` → Iteration 1 会实现（bge-base-zh + ChromaDB）

---

#### **3. generation.py（生成模块）**
**职责**：基于检索到的文档块，生成答案

**核心逻辑**：
```
用户查询 + 检索到的块 → 构建提示词 → 调用 LLM → 返回答案
```

**系统提示词设计**：
- 只能用给定资料作答
- 不能使用外部知识
- 信息不足时回答"未找到充分依据"
- 答案需要标注引用片段编号 [片段1]

**API 调用**：
- 如果有 `DEEPSEEK_API_KEY` → 调用 DeepSeek API
- 没有 API Key → 回退到模拟模式（返回 `[MOCK]`），保证链路仍能跑通

---

#### **4. scoring.py（评分模块）**
**职责**：评估检索和生成的质量

**核心指标**：
- **Recall@K（召回率）**：检索到的 k 个块中，是否包含正确答案所在的块
  
**核心函数**：
- `hit(retrieved_chunks, gt_doc_id, gt_start, gt_end)` → 判断检索是否命中
  - 检查逻辑：块的文档 ID 匹配 + 字符区间有重叠 → 命中
  
- `aggregate_by_category(results)` → 按类别计算召回率
  - 输出每个类别的 Recall@K + 总体召回率

---

#### **5. run_eval.py（主评估脚本）**
**职责**：串联所有模块，执行完整的评估流程

## 🔄 完整调用链路

```
┌─────────────────────────────────────────────────────────────┐
│ run_eval.py (主控)                                           │
└─────────────────────────────────────────────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
  ┌──────────┐        ┌─────────────┐      ┌──────────────┐
  │ 加载语料  │        │  加载查询集  │      │  设置参数    │
  │          │        │             │      │ (k, chunk_size)│
  └──────────┘        └─────────────┘      └──────────────┘
        │
        ▼
  ┌──────────────────────────────────────┐
  │ chunking.build_corpus_chunks()       │
  │ 将所有文档切成块池                    │
  │ 输出: [{doc_id, start, end, text}]   │
  └──────────────────────────────────────┘
        │
        │ 对每条查询执行：
        │
        ├──► ① retrieval.retrieve_random(query, chunks, k)
        │       └─ 随机返回 k 个块
        │
        ├──► ② generation.generate_answer(query, retrieved_chunks)
        │       ├─ 构建提示词（系统提示 + 资料片段 + 问题）
        │       ├─ 调用 DeepSeek API（或降级到 mock）
        │       └─ 返回生成的答案
        │
        ├──► ③ scoring.hit(retrieved, gt_doc_id, gt_start, gt_end)
        │       └─ 判断检索是否命中正确答案
        │
        └──► 收集结果: {id, query, category, hit, answer}
                │
                ▼
        ┌──────────────────────────────┐
        │ scoring.aggregate_by_category│
        │ 计算各类别的 Recall@K         │
        └──────────────────────────────┘
                │
                ▼
        ┌──────────────────────────────┐
        │ 输出到 results.json           │
        │ - 配置参数                    │
        │ - 各类别分数                  │
        │ - 每条查询的详细结果          │
        └──────────────────────────────┘
```

## 💡 具体执行示例

假设有一条查询：

```json
{
  "query": "SmartLock-100 如何生成临时密码？",
  "doc_id": "doc1",
  "char_start": 716,
  "char_end": 748
}
```

**执行流程**：

1. **chunking** → 把 doc1 切成多个块，其中一个块包含 716-748 这段文本

2. **retrieval** → 随机选 5 个块（Iteration 0 不管查询内容）
   - 可能选中：[chunk_8, chunk_3, chunk_12, chunk_1, chunk_7]

3. **generation** → 把这 5 个块 + 查询发给 DeepSeek：
   ```
   资料：
   [片段1] chunk_8的内容...
   [片段2] chunk_3的内容...
   ...
   
   问题：SmartLock-100 如何生成临时密码？
   ```

4. **scoring** → 检查这 5 个块中是否有任何一个：
   - 来自 doc1
   - 且字符范围与 716-748 有重叠
   - **命中 → hit=1；未命中 → hit=0**

5. **aggregation** → 对 32 条查询的 hit 求平均 → Recall@5

---

## 📊 为什么现在的分数会很差？

因为 **retrieval 是随机的**！

- 假设总共有 50 个块，随机选 5 个
- 理论召回率 ≈ 5/50 = 10%
- **这是刻意的**——建立性能下限，后续迭代才有对比基准

## 🚀 后续迭代路线

| 迭代 | 改进点 | 预期效果 |
|------|--------|----------|
| **Iteration 1** | 用向量检索替换随机检索（bge-base-zh） | Recall@K 从 ~10% 跳到 ~60% |
| **Iteration 2** | 优化分块策略（语义边界、滑动窗口） | 再提升 10-15% |
| **Iteration 3** | 混合检索（向量 + BM25 关键词） | 处理专有名词查询 |
| **Iteration 4** | 加入 Reranker（重排序） | 提升 top-5 的准确性 |
| **Iteration 5** | LLM-as-Judge 自动评估忠实度 | 自动化质量评估 |
| **Iteration 6** | 引用标注 + 拒答机制 | 减少幻觉 |
| **Iteration 7** | CI/CD 评估闭环 | 持续监控和改进 |

## 🎓 关键设计理念

1. **先证伪，再优化** → 没有测试集和指标，无法判断改进是否有效
2. **迭代式发现问题** → 每一层的问题，在下一层被发现和解决
3. **最小化起步** → 不用重框架（LangChain），手写代码理解每个细节
4. **可降级设计** → 没有 API Key 也能跑（mock 模式）

这就是整个项目的架构和调用链条！当前是 Iteration 0，只是验证链路通了，真正的优化从 Iteration 1 开始。
