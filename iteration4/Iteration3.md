# Iteration 3 验收报告

## 目标

实现 Hybrid Search（混合检索），结合向量检索和 BM25 关键词检索的优势，使用 RRF（倒数排名融合）算法合并结果。目标是解决 Iteration 2 中遗留的 ID 7（术语不一致问题），将 overall Recall 从 0.97 提升到 1.00（32/32 全部命中）。

## 验收标准

✅ **技术目标**：实现 BM25 检索和 Hybrid Search（向量 + BM25 + RRF 融合）  
⚠️  **性能目标**：overall Recall 提升到 1.00（实际：未达成，但有重要发现）

## 实验配置

### 技术栈

| 组件 | 选择 | 版本/参数 |
|------|------|----------|
| **Chunking 策略** | small_100_50 | Iteration 2 最优策略 |
| **向量检索** | bge-base-zh-v1.5 + ChromaDB | Iteration 1/2 baseline |
| **关键词检索** | BM25Okapi + jieba 分词 | 新增 |
| **融合算法** | RRF (Reciprocal Rank Fusion) | k=60（论文经验值）|
| **召回数量** | k_vector=20, k_bm25=20 | 最终返回 top-5 |

### 三种检索模式对比

| 模式 | 描述 | 预期优势 | 预期劣势 |
|------|------|---------|---------|
| **vector** | 纯向量检索 | 语义理解强 | 可能漏掉精确关键词 |
| **bm25** | 纯关键词检索 | 精确匹配（产品型号、编号） | 无法理解同义词、语义 |
| **hybrid** | 向量 + BM25 + RRF | **结合两者优势** | 召回噪声可能影响排序 |

### RRF 算法原理

**核心公式：**
```
RRF_score(doc) = Σ 1/(k + rank_i)
```

**优势：**
- 无需调参（不需要设置向量和 BM25 的权重）
- 量纲无关（向量相似度 0-1，BM25 分数 0-∞）
- 基于排名而非分数，更鲁棒

**处理平局策略：**
- 当 RRF 分数相同时，优先保留向量检索中排名更高的文档
- 原因：语义理解通常比关键词匹配更符合现代 RAG 的核心能力

## 🔍 意外发现：Chunking 策略显著影响 BM25 效果

### 实验结果

**预期：** Hybrid 在所有场景下都优于单一检索器  
**实际：** Hybrid 的效果**高度依赖 chunking 策略**

### 核心发现

#### **发现 1：块长度显著影响 BM25 性能**

| Chunking | BM25 Overall | BM25 chunk_sens | BM25 semantic | 评价 |
|----------|-------------|----------------|---------------|------|
| **fixed_200_40（长块）** | **0.94** ✅ | 0.80 | 1.00 | 优秀 |
| **small_100_50（短块）** | **0.88** ❌ | 0.70 | 0.91 | 较差 |
| **提升** | **+6.8%** | +14% | +10% | 显著！|

**原因分析：**

**短块问题（100 字符）：**
```
查询："SmartCam-200 的声音报警音量怎么调节？"

短块可能被切成：
- Chunk A: "SmartCam-200 是一款..." （只有产品名）
- Chunk B: "可设置触发移动侦测时..." （只有功能）
- Chunk C: "音量可调（70dB/80dB/90dB）" （只有答案片段）

问题：每个块包含的关键词太少，BM25 分数分散
```

**长块优势（200 字符）：**
```
长块：
"SmartCam-200...可设置触发移动侦测时摄像头发出警笛声，
音量可调（70dB/80dB/90dB）。启动隐私模式后..."

优势：
✅ 一个块包含多个关键词（SmartCam-200, 设置, 触发, 音量）
✅ BM25 累积分数更高
✅ 上下文更完整，关键词共现更多
```

#### **发现 2：Hybrid 只在"势均力敌"时有效**

**fixed_200_40 策略（vector 和 BM25 实力相近）：**
```
vector:  0.94  ←┐
bm25:    0.94  ←┤ 两者势均力敌
hybrid:  0.97  ←┘ RRF 融合发挥互补作用 ✅
```

**small_100_50 策略（vector 远强于 BM25）：**
```
vector:  0.97  ←  Vector 很强
bm25:    0.88  ←  BM25 较弱
hybrid:  0.94  ←  被 BM25 噪声拖累 ❌
```

**核心原理：**
- RRF 融合给两个检索器**相等的权重**（基于排名，不看分数）
- 当一个检索器明显更强时，融合反而会被弱者拖累
- 当两者实力相近时，融合才能真正互补

#### **发现 3：Hybrid 在长块上解决了额外的失败案例**

**chunking_sensitive 类别的提升：**

| Chunking + Mode | chunking_sensitive | 差异 |
|----------------|-------------------|------|
| fixed_200_40 + vector | 0.80 | baseline |
| fixed_200_40 + bm25 | 0.80 | 持平 |
| **fixed_200_40 + hybrid** | **0.90** | **+12.5%** ✅ |
| small_100_50 + vector | 0.90 | Iteration 2 最优 |
| small_100_50 + hybrid | 0.80 | 退步 10% ❌ |

**说明：**
- 在 fixed_200_40 上，hybrid 成功解决了 1 个 vector 和 BM25 都失败的案例
- 在 small_100_50 上，hybrid 反而引入了新的失败（ID 9）

### 案例 1：ID 7 - 两个检索器都失败（符合预期）

**查询：** "SmartPlug-400 的充电保护功能是怎样工作的？"  
**文档：** "检测到设备电流...自动关闭插座，**防止过充**"

**问题：** 术语不一致（"充电保护功能" vs "防止过充"）

**在 small_100_50 策略下：**

| 检索模式 | 答案块排名 | 结果 |
|---------|-----------|------|
| Vector | chunk 75 排第 11（top-20 内但不在 top-5）| ❌ |
| BM25 | chunk 74 排第 17（top-20 内但不在 top-5）| ❌ |
| Hybrid | 两个检索器都没把答案排进 top-5 | ❌ |

**在 fixed_200_40 策略下：**

| 检索模式 | 结果 |
|---------|------|
| Vector | ❌ 未命中 |
| BM25 | ❌ 未命中 |
| Hybrid | ❌ 未命中 |

**分析：**
- 答案块在两个检索器中的排名都太靠后
- RRF 融合无法"凭空"提升排名，只能合并已有的排序
- **结论：Hybrid 无法解决召回阶段的遗漏问题**

### 案例 2：ID 9 - BM25 噪声干扰（仅在 small_100_50 上发生）⚠️

**查询：** "SmartCam-200 的声音报警音量怎么调节？"  
**答案位置：** doc2, chunk 27

**在 small_100_50 策略下：**

| 检索模式 | Top-5 中是否包含答案块 | 结果 |
|---------|---------------------|------|
| Vector | ✅ 第 3 名（chunk 27）| 命中！|
| BM25 | ❌ 未进入 top-5（返回了其他 doc2 的块）| 失败 |
| Hybrid | ❌ chunk 27 被挤出 top-5 | 失败！|

**在 fixed_200_40 策略下：**

| 检索模式 | 结果 |
|---------|------|
| Vector | ✅ 命中 |
| BM25 | ✅ 命中 |
| Hybrid | ✅ 命中 |

**详细排名对比（small_100_50）：**

```
Vector Top-5:
  1. doc2, chunk 19
  2. doc3, chunk 35
✓ 3. doc2, chunk 27  ← 答案块，命中！
  4. doc1, chunk 17
  5. doc5, chunk 60

BM25 Top-5:
  1. doc2, chunk 19
  2. doc5, chunk 66  ← 噪声块（完全无关）
  3. doc3, chunk 35
  4. doc2, chunk 25
  5. doc3, chunk 36

Hybrid (RRF 融合) Top-5:
  1. doc2, chunk 19
  2. doc3, chunk 35
  3. doc5, chunk 66  ← BM25 的噪声块挤进来了！
  4. doc5, chunk 60
  5. doc2, chunk 25  ← 答案块 (chunk 27) 被挤出去了！
```

**关键问题：**
- Vector 正确找到了答案块（chunk 27，排第 3）
- BM25 返回了噪声块（chunk 66，doc5 与 doc2 完全无关）
- RRF 融合时，chunk 66 因为在 BM25 中排名第 2，获得较高 RRF 分数
- **结果：噪声块挤掉了正确答案块！**

**为什么在 fixed_200_40 上没有这个问题？**
- 长块包含更多关键词，BM25 能更准确地找到相关文档
- 短块关键词太少，BM25 容易返回不相关但恰好匹配某个词的块

**RRF 分数计算示例（k=60）：**
```python
# chunk 27（答案块）
vector: 第 3 名  → RRF += 1/(60+3) = 0.0159
bm25:  未出现    → RRF += 0
总分: 0.0159

# chunk 66（噪声块）
vector: 未出现   → RRF += 0
bm25:  第 2 名   → RRF += 1/(60+2) = 0.0161
总分: 0.0161

# chunk 66 的 RRF 分数 (0.0161) > chunk 27 的分数 (0.0159)
# 结果：噪声块排名更高！
```

## 深度洞察

### ✅ 已验证的假设

1. **块长度显著影响 BM25 效果**
   - 长块（200字符）→ BM25 提升 6.8% overall
   - 原因：更多关键词，更高的累积分数，更完整的上下文

2. **Hybrid 效果高度依赖两个检索器的实力对比**
   - **势均力敌时**（fixed_200_40: vector=0.94, bm25=0.94）
     - Hybrid 发挥互补作用 → 0.97 ✅
   - **实力悬殊时**（small_100_50: vector=0.97, bm25=0.88）
     - Hybrid 被弱者拖累 → 0.94 ❌

3. **两种达到 0.97 的最优路径**
   - **路径 1**：small_100_50 + vector（细粒度 + 强语义）
   - **路径 2**：fixed_200_40 + hybrid（粗粒度 + 互补融合）
   - **选择依据**：计算资源、检索偏好、块数限制

### ❌ RRF 的局限（新发现）

1. **无法解决召回问题**
   - 如果两个检索器都没把答案排进召回范围（如 ID 7），RRF 无能为力
   - RRF 只是"融合排名"，不能"创造新排名"

2. **噪声放大效应（仅在短块上）**
   - 当某个检索器返回不相关的块时，RRF 会给这些块一定的权重
   - 如果噪声块在某个检索器中排名很高，可能挤掉正确答案（如 small_100_50 的 ID 9）
   - **长块上这个问题不明显**，因为 BM25 更准确

3. **无法理解内容**
   - RRF 只看排名，不看文档内容和查询的真实匹配度
   - 无法判断"这个块虽然排名高，但其实不相关"

### 🎯 Chunking × Retrieval 的适配矩阵

| Chunking 策略 | 最适合的检索方式 | Overall Recall | 原因 |
|--------------|----------------|---------------|------|
| **small_100_50（短块）** | **Vector** | **0.97** 🏆 | 精确的局部语义，不依赖关键词数量 |
| **small_100_50** | BM25 | 0.88 ❌ | 关键词太少，分数分散 |
| **small_100_50** | Hybrid | 0.94 | BM25 噪声干扰 |
| **fixed_200_40（长块）** | Vector | 0.94 | 语义稍微模糊（块太大）|
| **fixed_200_40** | BM25 | 0.94 | 关键词丰富，上下文完整 |
| **fixed_200_40** | **Hybrid** | **0.97** 🏆 | 两者势均力敌，互补效应 |

### 💡 为什么有两个最优组合？

**small_100_50 + vector（细粒度路径）：**
- ✅ 每个块语义聚焦，向量表示更精确
- ✅ 块数多（85），覆盖度高
- ❌ 索引开销大，存储成本高

**fixed_200_40 + hybrid（粗粒度路径）：**
- ✅ 块数少（28），索引快，存储省
- ✅ 长块让 BM25 性能提升，与 Vector 形成互补
- ❌ 需要同时运行两个检索器

**选择建议：**
- **追求极致性能**：两者都可以（都是 0.97）
- **资源受限**：fixed_200_40 + hybrid（块数少 3 倍）
- **系统简化**：small_100_50 + vector（单一检索器）
- **关键词重要**：fixed_200_40 + hybrid（BM25 在长块上强）

### ✅ 已验证的能力

1. **BM25 检索实现成功**

### ⚠️ 已发现的局限

1. **Hybrid 不一定优于单一检索器**
   - 在语义理解为主的数据集上，Hybrid 可能被 BM25 拖累
   - RRF 无法识别和过滤噪声块
   - 需要更智能的融合策略（如 Reranker）

2. **召回范围的重要性**
   - ID 7 的失败说明：答案块在两个检索器中都排名靠后（11-17 名）
   - 即使扩大召回到 k=40，仍无法通过 RRF 融合挽救
   - 需要从根本上提升召回质量

3. **术语不一致问题依然存在**
   - "充电保护功能" vs "防止过充"
   - 向量检索的语义理解也有局限
   - 可能需要其他技术（如查询改写、同义词扩展）

3. **无拒答机制**

4. **无评估闭环**
   - 手动运行评估，无法持续监控
   - 需要 Iteration 7 的自动化流程

## Iteration 4 的价值与必要性

### 为什么需要 Reranker？

| 问题 | RRF 的局限 | Reranker 的优势 |
|------|-----------|----------------|
| **ID 7（召回失败）** | 答案块不在召回范围内 | ❌ 无法解决（超出能力范围）|
| **ID 9（噪声干扰）** | 基于排名融合，无法识别噪声 | ✅ Cross-encoder 理解内容，过滤噪声 |
| **通用场景** | 只看排名，不看匹配度 | ✅ 重新评估 query-doc 相关性 |

### Reranker 的工作原理

**当前 RRF 流程：**
```
Vector top-20  ─┐
                ├─→ RRF 融合（只看排名）→ top-5
BM25 top-20   ─┘
```

**Iteration 4 Reranker 流程：**
```
Vector top-20  ─┐
                ├─→ RRF 融合 → top-20 候选
BM25 top-20   ─┘
                    ↓
              Reranker（cross-encoder）
           理解 query-doc 匹配度
                    ↓
                 top-5（精排）
```

**Reranker 的优势：**
1. **内容理解**：不只是融合排名，而是重新评估每个文档与查询的匹配度
2. **噪声过滤**：可以识别"排名虽高但不相关"的块（如 ID 9 的 chunk 66）
3. **更高精度**：Cross-encoder 同时编码 query 和 document，比 bi-encoder（向量检索）更精确

## 实验性探索：多粒度混合检索（Multi-Granularity Hybrid Search）

### 实验动机

基于前面的发现：
- **short块（small_100_50）+ Vector**: 0.97（语义精确）
- **long块（fixed_200_40）+ BM25**: 0.94（关键词丰富）

**实验假设：** 如果让 Vector 使用短块，BM25 使用长块，能否突破 0.97 的上限？

### 实验设计

```python
retrieve_hybrid_multi_granularity(
    query=query,
    corpus_dir='corpus',
    k=5,
    strategy_vector='small_100_50',  # Vector 用短块（85块）
    strategy_bm25='fixed_200_40',    # BM25 用长块（28块）
    k_vector=20,
    k_bm25=20,
    rrf_k=60
)
```

**核心挑战：** 不同粒度的块需要对齐和去重

### 去重策略

#### 第一次去重：位置相同的块
```python
# 判断标准：(doc_id, start, end) 完全相同
# 目的：合并同一个块的重复对象，RRF 分数累加
unique_candidates[key] = chunk
unique_candidates[key]['rrf_score'] = rrf_scores.get(key, 0)
```

#### 第二次去重：位置重叠的块
```python
# 判断标准：内容重叠率 > 50%
overlap_ratio = overlap_length / min(chunk1_length, chunk2_length)

if overlap_ratio > 0.5:
    if candidate.length > selected.length:
        # 保留更长的块（更多上下文）
        replace(selected, candidate)
```

**设计思想：**
- 优先保证 RRF 分数高（相关性）
- 重叠时优先保留长块（上下文完整性）

### 实验结果

| 指标 | 分数 | 对比历史最优 |
|------|------|-------------|
| **overall** | **0.97** | 与最优持平 |
| chunking_sensitive | 0.90 | 持平 |
| exact_match | 1.00 | 持平 |
| semantic_paraphrase | 1.00 | 持平 |

**失败案例：** 1个（ID 7，与历史最优相同）

### 实验结论

**✅ 技术上可行：**
- 成功实现了不同粒度块的对齐和去重
- 去重策略运行正常（两次去重分别处理位置相同和位置重叠）

**❌ 性能无提升：**
- 达到 0.97，与现有最优方案持平（未突破）
- 唯一失败案例仍是 ID 7（术语不一致问题）

**⚠️  工程复杂度高：**
- 需要构建两套不同粒度的块索引
- 需要复杂的重叠检测和去重逻辑
- 代码量增加约 150 行

**决策：保留代码，不推荐生产使用**

原因：
1. 性能无增益（0.97 = 0.97）
2. 工程复杂度显著增加
3. 存在更简单的方案达到同样效果
